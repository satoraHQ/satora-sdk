The hash an EVM lock is created under is now fixed by the client and checked on every funding path. For EVM → Lightning it is the payment hash of the invoice the caller supplied, or (for a Lightning address / LNURL, which the server resolves) that of the invoice the server returned, checked against its `hash_lock` and quoted payout; it is stored as `StoredSwap.lightningPaymentHash`. EVM → Bitcoin / Arkade use the client's own preimage hash. `fundSwap` (Permit2, native, CCTP-inbound), `fundSwapFromSolana`, `fundSwapGasless`, `continueRefundedEvmSwap`, `getCoordinatorFundingCallDataPermit2` and `getPermit2FundingParamsUnsigned` refuse a server hash lock that differs, before anything is signed; a swap without the record (recovered, or created by an older SDK) can be refunded but not funded.

Every funding payload is also bound to the swap's funding terms, recorded from its creation response (`StoredSwap.evmFundingTerms`): the Permit2 spender must be the coordinator named at creation (and the one recorded at funding, if any), the claimer, timelock, source and lock token must match, the amount may not exceed the input, the calls must match their hash, carry no native value, and may touch the source token only to pay a relay fee to the server (capped, default 0) or approve at most the input to a router the batch calls; they may not touch the lock token. What gets signed is built from those terms. The native lock's HTLC, claimer and timelock are checked too. A swap without recorded terms (recovered, or created by an older SDK) cannot be funded.

New: `FundingPins` (`allowedCallTargets`, `maxSourceAmount`, `maxRelayFee`) as `options.funding` on `fundSwap`, `fundSwapFromSolana`, `fundSwapGasless`, `continueRefundedEvmSwap`, `getCoordinatorFundingCallDataPermit2` and `getPermit2FundingParamsUnsigned`; `checkFundingPayload`, `EvmFundingTerms`, `ExpectedFunding`, `invoiceAmountMsat`; `getEvmFundingExpectation(swapId, pins?)`. **Breaking:** `buildCctpInboundBatch`, `submitCctpInboundUserOp`, `submitCctpInboundBalanceUserOp`, `cctpFundSwap` and `cctpFundSwapFromSolana` take a required `expected: ExpectedFunding`. **Behaviour:** gasless funding on a chain whose relay charges a fee (Ethereum) needs `funding.maxRelayFee`; a payout-pinned swap re-quoted above the input recorded at creation needs `funding.maxSourceAmount`.

`retrySwapWithInvoiceWithSigner` and `retrySwapWithInvoice` move only this swap's own lock: a funding receipt from any source counts only for a `SwapCreated` under that client-held hash, created by the depositor and still active (followed through the local rehash history), and every term the server signs must match it. The server's refund calldata is decoded, checked (one of the refund calls the server builds, on this swap's HTLC or coordinator, paying one of this client's addresses, and with a signer an active lock) and re-encoded by the client, never sent as given; a refund of a lock rehashed elsewhere falls through to that checked call. A sponsored rehash is recorded before it is sent, dropped only when it failed before the send, and a record without its tx is followed only through the receipt its UserOp hash leads to.
